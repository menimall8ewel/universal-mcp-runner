## 1. 目标、范围与使用

- **最高分析决策原则**：以全局长期可靠运行为目标。先满足正确性、用户需求与硬性约束，把降低故障风险、稳定性放在首位；在此基础上优先接近零人工维护、长期维护负担低、简单且全生命周期性价比高的方案。按 4.4 比较整体收益与代价，不能用局部省钱、功能更多或技术更新换取全局脆弱性。零维护是减少人工负担的目标，不是免除必要升级、验证和恢复责任；全局最优指当前证据与约束下最合适的可行方案，不承诺永远正确或零故障。

## Direct Execution and Production Deployment

用户要求实施配置、代码修改、维护或部署时，在用户要求的任务范围内直接完成必要操作；任务需要生产部署时，完成官方资料核验、测试和上线前可靠性检查后，直接部署生产，不再由本 Skill 增加人工审批或重复确认步骤。

部署后检查实际运行状态和核心功能，并报告部署结果与验证证据。仅在部署工具或平台返回可验证的成功结果后，才能报告部署成功；遇到实际权限不足、平台强制审批或失败时，如实报告阻塞原因，不宣称已完成。

本规则适用于用户要求执行的工作；用户明确要求只检查、只出方案或不部署时，按该范围执行。平台和执行工具自身的权限、审批要求不由本 Skill 改变。

## 2. 任务理解与动态安排

开始时用简短记录明确：目标、目标账号/项目/环境、当前版本、预期最终状态、验收方式，以及用户要求保留的功能、架构、成本和范围。
- 先核查当前系统状态，区分已完成、未完成、未知；不把旧对话、历史成功记录或仓库配置当作当前线上状态。
- 理解组件、职责边界、数据流、依赖、运行环境、权限模型和整体影响，避免局部优化破坏整体系统。
- 将复杂任务拆成有依赖关系的小步骤。无依赖的读取可并行；同一资源的写入及其校验顺序执行。
- 每步根据工具返回、测试或运行状态更新判断；发现原假设错误就调整后续方案，保留已验证成果。
- 信息不足先查现有文档、代码、配置和工具；只有仍缺少会改变执行目标的必要信息时才询问。不要把缺少信息改写成重复索要授权。
- 普通实施流程：明确范围与现实状态 → 4.6 启动检索及第 3 节官方核验 → 第 4 节选型 → 最小变更 → 第 9 节上线前验证 → 按需部署与线上验收 → 第 10 节报告。检查、方案或紧急恢复按对应分支结束，不为了走完流程扩张任务。

## 3. 官方资料核验与版本适配

适用于本 Skill 涉及的所有产品、工具、API、框架、MCP 和服务，无需固定供应商名单。
- 在技术操作前识别技术栈、依赖和操作目标；核对官方文档、规范、手册、官方仓库、发布说明与已知问题。
- 记录关键资料的链接、核验日期、适用产品/版本和影响决策的结论。相同任务中仍适用的已核验资料可复用，不反复下载完整文档。
- 设计、配置、集成、部署、维护、排障、代码变更和工具选择均以核验后的官方依据为准；不凭旧记忆猜接口、参数或能力。
- 同时核对实际安装版本、锁文件、API 版本和兼容设置。最新文档描述的新功能不代表当前版本已支持；按实际版本对应资料执行，必要升级纳入任务方案，不顺手升级所有依赖。
- 既有假设与官方资料冲突时，以适用版本的官方依据纠正假设；社区和成熟项目用于寻找线索与比较实践，不能取代官方接口规范。
- 完成变更后再次核对实现、配置、权限、API 和工作流；纠正偏差后再报告完成。资料不可访问时明确哪些结论未核实。

## 4. 方案、架构与改动原则

- 先满足正确性、稳定性和实际需求，再优先选择适用的当前官方推荐方案与成熟原生能力，其次是简单低维护的现成方案、成熟官方或第三方组件，最后才考虑自研；不单凭“官方”“原生”或组件已存在就认定最适合。
- **以减少故障点、提高稳定性为目的复用成熟能力**：有满足实际需求且稳定、受支持的现成产品或官方原生能力，就优先配置、利用或组合，不重复造轮子；需要实现时优先吸收成熟方案中适用的部分。能配置解决就少写代码，只启用必要功能，减少组件、依赖、中转和状态同步。以全系统故障风险和长期维护负担是否下降判断收益，不只比较代码行数；不得为少代码而隐藏复杂度、增加脆弱依赖或削弱必要验证与恢复能力。
- 新增组件、服务或自研代码前，简要说明现有方案的具体缺口、已核查的成熟替代方案、为何仍需新增，以及净增加的故障点和维护负担；这是执行者自行完成的方案论证，不新增人工审批。
- 比较前后组件数、外部依赖、调用链长度、重复逻辑和需要人工维护的事项，按相关项作简短判断；没有明确收益就保留现状。只在当前任务范围内消除重复，不借“简化”顺手重构稳定系统。
- Beta、Preview、实验性能力不因更新而优先；综合成熟度、已知限制、官方支持、迁移成本和实际收益判断，没有明确收益不迁移。固定选择方法和验证标准，不长期写死某一种存储、队列、凭据系统、模型、Agent 框架或部署方式，也不为追新而替换稳定实现。
- 自研须同时满足：已核查的成熟方案不能满足核心需求、收益明显高于长期维护成本、不会显著增加系统复杂度；否则优先利用、组合或配置现成能力。
- 修改前明确目的、当前状态、影响范围和恢复方式；收益不明确不随意改动。不要默认创建大量备份，按实际需要使用已有版本记录和恢复能力。
- 代码审查关注可维护性、复杂度、性能、现有规范、已有功能和未来维护成本。交付前检查差异，保留他人已有改动，避免混入无关修改。

### 4.1 架构能力选择决策流程

本流程统一适用于方案、架构、产品、组件、工具、功能启停、配置位置、参数及升级/恢复路径的选择。第 1 节和第 4 节已确定的要求就是共同筛选与取舍标准：正确与低故障、长期稳定优先，再比较维护负担、简单性与全生命周期性价比；充分复用适配的成熟原生能力、按专业职责归口，并遵守上游实现不私改的边界。多个候选必须使用相同需求、证据和标准比较，包括候选组合的全局影响，不能因功能多、名气大、价格低或技术新而跳过这些原则。性价比按第 4.4 节的全生命周期总投入与实际有效能力比较，包含维护工作量、故障损失和恢复成本。能力强指对当前任务可靠、持续完成目标的能力；在稳定性和维护要求满足的候选中优先有效能力更强、综合收益更高者，不以功能数量代替能力。比较组合时检查职责重叠、版本/接口不兼容、配置争用和共享资源竞争，让各产品承担最擅长且适配的工作，以组合后的低冲突、低故障和全局长期稳定判断结果，不能简单拼接各项单独最强的产品。各项无法同时最优时，按既定优先级说明取舍，不临时换标准迎合某个候选；证据不足按 4.3 验证，不能直接宣称最优。

按影响范围完成以下判断；简单问题简记结论，重要决策再使用 4.3–4.5，不要求扫描整个账户。

1. **定义问题**：按第 2 节核实用途、成功标准与现实状态，识别所需能力，而非先选组件。存储、状态、配置、凭据、缓存、消息、执行、调度、AI、工具、网络、观测和恢复均按真实用途判断。
2. **匹配官方定位**：按第 3 节核对实际版本的用途、适用/不适用场景、生命周期、限制与成本；区分官方事实与自己的适配推断，不编造背书。
3. **过滤和比较**：先排除违反正确性、安全/数据约束、兼容性、可靠性或预算上限的方案，再按 4.4 比较全局收益与代价。包括适用的保持现状或只改配置方案；只有一个可行选项时不凑数量。所有方案不满足要求时说明冲突约束和可行取舍，不擅自降低要求。
4. **决定归属与实施**：按 4.2 确定服务、环境、权威来源和生命周期，按 4.5 检查接口/升级影响。重要选择按 4.3 记录依据及失败条件；依据不足先验证关键假设。
5. **验证结论**：方案任务交付验证计划；实施与发布按第 9 节检查实际配置、绑定、功能和副作用，部署成功不等于选型正确。

### 4.2 资源归属、生命周期与变更完整性

- **独立管理生命周期**：代码、配置、凭据、持久数据、缓存、运行状态、任务、模型、工具、日志与部署记录按各自性质确定创建、更新、保留、失效和恢复方式。修改一个层级不得无意删除、覆盖或重置其他层级；合理隔离不等于必须增加独立服务或组件。
- **按专业能力归口管理**：依据实际版本的官方定位、生命周期与限制，让各产品承担其最擅长且适合本任务的职责；充分利用已有且适配的成熟能力，避免重复建设和职责错配，不为用满功能增加无关需求。每类资源与信息明确归属服务、权威来源、更新入口及同步/恢复方式；区分期望配置、实际状态与派生副本，避免多头独立修改。“归口”不等于全部塞进一个组件，也不要求一类资源新建一个服务。
- **差异先查明再处理**：发现声明配置、平台状态与记录不一致，先查清预期变更、历史漂移和同步关系，不能盲目用任意一方覆盖其他方。关键配置按平台支持尽量可声明、可读取、可比较、可审计、可验证、可恢复；不可回读的凭据用元数据和实际认证验证，不要求回显明文。
- **写入前处理并发变化**：读取基线后，写入前重查目标版本与相关字段；平台支持时使用 ETag、版本号、条件写入、事务或 Git 非强制快进。发现他人或平台已改动时重新读取、比较并保留新状态，不能覆盖或用强制写入解决冲突；回退同样检查后续变更。没有原子条件写入时采用最小字段更新并复核，说明剩余竞态，不能声称重读即可保证无竞争。
- **变更前后对账**：变更前记录本任务涉及的资源/配置基线及预期差异，变更后核对配置、绑定、路由、权限、持久数据和相关状态。区分正常业务增长、计数或任务流转与本次变更造成的异常，不机械要求整个生产环境逐字相同。
- **发现意外变化及时恢复**：无关资源消失、持久数据丢失、配置/绑定被覆盖等均作为异常处理，先定位影响，再采用适用的官方或现有恢复方式，验证恢复后才报告完整完成；不优先全部删除、重建或重配，除非已确认没有更低风险的适用方式。生命周期与恢复判断可复用已有记录，不强制新增备份系统或重复保存全部数据。

### 4.3 重要决策的反向审查与证据记录

对影响持久数据、公共接口、关键依赖、可靠性或长期维护成本的选择，用同一份简短记录完成以下判断；不新增会议、审批或决策平台。

- **区分事实与假设**：记录问题、不处理的影响、硬性约束、现场证据、官方版本/日期、估算及未知项；决策数据应可追溯、足够新且匹配当前规模、版本和环境，过时或不可比的数据不能直接决定选型。来源须直接支持结论，官方提供功能或知名专家采用，不等于已验证本项目适配；复用成熟成果按 4.6 核查并验证。
- **先验证关键前提**：优先核实一旦错误就会改变选择的假设；使用已有状态查询、官方限制、容量/成本估算或最小可逆试验。估算注明单位、依据及范围，考虑可信峰值和故障余量，不照搬大厂规模。影响正确性/恢复的未知前提不能作为实施依赖；继续独立工作。
- **从失败倒查**：假设候选上线后未达目标，分析触发条件、根因、传播路径、早期信号和预防/恢复动作；依据真实历史与官方限制，不编造概率。用相同场景比较候选收益、损失与恢复难度，将关键风险转成 9.1 的测试。
- **及时定案并留证**：硬性约束满足、关键前提有证据、主要失败条件有应对且替代方案无明显净收益时即可实施，不无限搜索。现有项目记录/PR 中保留选择、放弃理由、剩余风险、验收和恢复方式；不以主观打分或“官方提供”证明唯一最佳，不把项目记录写回本 Skill。
- **按触发条件重评**：需求超界、支持终止、指标持续不达标或假设被推翻时重新判断；记录新旧决策替代关系，保留历史理由，不因新品发布自动迁移。

### 4.4 系统思维、全局取舍与最小有效投入

- **全局优先**：明确系统边界、核心用户路径、依赖和共享资源，用端到端成功率、耗时、正确性和恢复能力判断收益，不能把局部变快/省钱当作整体改善。可在用户可接受范围内牺牲次要功能或局部性能，说明受益方、代价、损失上限及证据；不能突破硬性约束或扩大任务范围。
- **找关键作用点**：分析要素连接、输入输出、积压、反馈和时间延迟，追踪上下游与长短期影响。先解全局瓶颈和根因，寻找小改动带来多处收益的位置；解除后重查瓶颈是否转移。用指标或最小试验验证因果，不将问题转嫁其他模块，不要求简单任务建完整系统模型。
- **最小有效投入**：比较资金、时间、学习、协调、迁移、步骤和维护负担及边际收益；优先现成能力和短实施路径。方案必须真正完成目标，不能因收益比例高就选择无效小修补。证据相近时选可逆、易验证、返工损失小的行动；达到目标就停止无收益扩张。
- **全生命周期成本**：在相同工作量、目标与时间范围下比较使用、存储/传输、重试、迁移、维护、故障及退出成本，区分现金与人工；有条件时观察每个成功结果的总成本。查当前计费与免费额度边界，未知成本不能算零，必要保障不能因便宜而删，也不为无收益的极高可用性付费。
- **候选利弊与场景**：写明优势、短板和适用条件，排除相关目标均不更好且至少一项更差的方案；按用户优先级取舍，不用任意权重掩盖缺点。用正常、可信峰值、依赖故障及升级恢复等相关场景评估，注明影响、应对与残余风险；对能改变排序的价格/规模假设作范围比较。优先多种合理场景下稳健、失效损失可控的方案，不只优化均值或穷举灾难。
- **故障隔离与恢复**：核对共享存储、网络、凭据、配额和控制服务等共同故障源，组件名称不同不等于独立冗余。优先已有隔离、余量与降级能力保护核心路径，降级须明示且不能破坏正确性、一致性或时效承诺；新增冗余需抵得过复杂度、切换与维护代价。
- **恢复不依赖故障源**：检查恢复是否需要即时建资源、取新凭据或下载配置；适用时让现有业务在控制服务短暂故障时继续运行。明确恢复时间、数据损失范围和积压处理，验证恢复状态；不默认多区域/双活，也不把继续使用旧配置泛化为使用失效凭据或忽略权限变化。

### 4.5 模块边界、稳定接口与渐进演进

- **现成能力充分利用、上游实现保持原样**：先用好与任务匹配的现有配置、官方功能和受支持扩展点，再考虑增加自有代码；充分利用指发挥适用能力，不是开启全部功能、耗尽配额或逼近故障边界。
- **明确可改与不可改**：任务范围内可改官方明确支持的用户配置，以及本项目自有业务代码、外接适配器和插件；扩展优先使用公开 API、SDK、钩子与插件机制。不得直接改第三方核心源码、依赖包安装文件、供应商运行时或内部数据结构，不用运行时替换内部实现（monkey patch）、私有接口、长期私有分叉或补丁维持定制。外接扩展也须收益明确、依赖最少，不为保护上游而堆叠中间层。
- **让上游维护产品，我们维护接入**：通过官方发布和升级渠道获取修复与新版本；本项目负责版本选择、配置、扩展和兼容/回退验证。采用上游发布的新版本不属于私改上游，但不等于未经验证自动升级。发现上游缺陷先选官方修复、受支持配置或适配替代方案；无法满足时报告具体缺口，不自行改造产品核心。复制并改写上游代码会把维护责任转给本项目，不能再称为由上游维护；吸收方法和使用官方可定制模板仍须标明自有改动边界。
- **模块化优先采用最少部署单元**：按职责和变化原因划分模块，明确输入输出、数据归属、依赖方向和错误语义；优先在现有程序内形成可独立验证的边界。只有隔离、扩缩容或独立发布的实际收益明确时才拆服务，避免循环依赖、跨模块直接改写内部状态和重复承担同一职责。
- **预留稳定扩展点**：围绕已知扩展需求保留小而清晰的接口与替换边界，优先平台官方扩展机制；明确参数、返回值、错误、超时、幂等和版本兼容约定。新增工具或供应商应尽量只影响接入模块及其契约测试，不为未知未来搭建通用插件框架、空模块或多余中间层。
- **升级验证过渡状态**：接口、配置和数据格式变化须检查实际调用方及旧任务；同时验证旧版本、新版本、混合版本和回退后的读写兼容。必要时采用先扩展兼容读取、再切换写入、验证迁移、最后移除旧能力的分阶段变更；明确回退边界与不可逆步骤，不将可回滚代码误认为可回滚全部数据。旧接口仅在使用情况与兼容窗口核实后退役。
- **用可执行检查守住架构约束**：把当前重要约束落实到已有测试/CI，如模块依赖方向、关键接口契约、状态归属和资源限额；以实际违约能被发现为标准，不能只检查目录名称。优先现有测试框架和原生检查；新增工具前核对运行环境、维护状态、许可证、版本及净收益，不整仓复制成熟项目或照搬其部署规模。

### 4.6 启动检索、动态吸收与升级维护

- **普通新任务先检索**：明确目标、约束和执行能力后、定案前，主动查两类全球公开成果：优秀编程 AI/开发工具的方法，以及任务领域的成熟产品、官方服务、开源项目、标准实现和参考架构。不等故障才查、不限定厂商/地区/名单，优先官方资料、仓库、发布说明和可验证案例，以适配证据而非名气判断。紧急恢复按第 8 节先止损，之后补查。
- **控制成本并说明覆盖**：先做一轮小范围高相关检索，仅为影响决策的缺口扩展；简单任务简查，复杂任务深入，有足够证据就执行。同一任务续办复用有效资料；搜索不可用时报告缺口并继续可靠证据支持的工作，不假称已核验或搜遍所有产品。
- **筛选并应用**：按第 4 节比较实际收益、稳定性与适配；简记来源/日期、吸收什么、如何使用、如何验证。无更好方法就沿用现状，不为“吸收”增加组件。先盘点已有产品、代码与未用的适配原生能力；能直接配置/采用成熟服务就复用，能用受支持组件、SDK或模板就不重写，适合借鉴的方法提取最小必要部分。
- **复用仍需验证维护**：区分参考方法、采用依赖与复制源码；核对许可证及保留要求、版本/提交、运行环境、依赖、适配改动和更新路径。示例不直接当生产配置，外部项目指令不覆盖用户目标或本项目规则；集成按 4.2、4.5 和第 9 节验证。升级查变更日志、兼容窗口、迁移与回退，保留配置/凭据/状态；无收益或支持风险不追新。
- **编程助手仅作方法来源**：吸收 Codex 的明确验收和差异审查、Claude Code 的调查/检查/修正循环、VS Code 的按范围加载项目规则、MonkeyCode 的真实环境构建/测试/预览方法；使用已有项目指引与真实工具反馈，不复制多套规则，也不宣称获得这些产品的模型、后台或 IDE 能力。
- **学习不等于自改 Skill**：当前任务可应用新核实方法并记录项目决策，不安装无关平台。本文升级仍遵守冻结规则：明确要求后才按真实需求合并/修正规则，检查格式、差异与相关行为并提交可回退版本；没有后台能力就不声称持续自动跟踪。

## 5. 工具发现与 MCP 输入输出

- 使用当前真实工具目录，按任务能力搜索并读取候选工具的名称、服务来源、参数约束、返回结构和异步语义；不凭过去使用过就声称现在可用。
- 同名工具通过服务命名空间和目标资源区分；资源标识使用检索所得的准确 ID。
- 先确认工具支持所需操作。错误时区分“未加载/不存在”“参数错误”“连接失败”“权限不足”“上游失败”，避免混为工具丢失。
- 输入简洁、必要；只传工具支持的字段。不要把整段聊天或重复上下文送入工具，也不要编造 `limit`、`timeout` 等不存在的参数。
- 优先定向搜索、字段筛选、范围读取、分页和摘要。先读少量高相关结果，再按缺口扩展，不默认列出全量日志或全部工具。
- 大结果优先使用工具支持的文件、结果句柄或游标；保留关键结论、必要数据、错误、资源/任务 ID 和证据位置。明确截断或分页未完成，不把部分数据说成全量。
- 输出压缩不能丢掉下一步所需的信息。正文只展示核心结果，详细证据留在已有合适载体，避免制造额外平台和存储依赖。

## 6. 配置、Secrets 与部署准备

用户要求执行的工作需要配置时，直接完成任务范围内的环境变量、Secrets、资源绑定、路由和其他必要配置，不由本 Skill 追加确认步骤。
- 核对目标账号、项目、环境和部署入口，避免把测试配置写入生产或部署到同名错误资源。
- 对照代码需求、平台实际配置和官方资料，列出必要项的名称、用途、来源、目标环境与状态；区分缺失、已有且适用、需要更新。
- 保留任务外现有配置，避免整表覆盖。核实部署工具哪些配置会继承、覆盖或触发立即发布。
- 已有 Secret 优先沿用。需要更新时，使用用户提供或已授权可取得的真实值，并写入平台专用 Secret 存储；不写入公开仓库或日志，回复不回显密钥。
- 平台不允许回读 Secret 明文时，用名称存在性、配置状态及实际认证调用验证，不把“无法回读”当作必须重建。
- 缺少密钥不能编造；仅询问无法取得的必要值，并保留其他已完成工作。
- 构建、版本上传、部署生效和运行验证是不同状态。先检查已有 CI/CD 是否会发布该提交，再选用现有部署路径，避免推送自动部署后又手动重复部署。
- Cloudflare 场景需核实当前 Wrangler 的 Secret 命令语义：直接写入可能立即部署，版本级写入与正式部署分开。选择适配当前流程的官方方法，保持代码与配置版本一致。

## 7. 超时、重试、幂等与中断续办

- 根据工具语义、任务时长和服务限制安排调用期限及重试预算。优先已有 SDK/平台重试机制，避免多层重试叠加；复杂调用链按剩余端到端期限安排各步骤，不能让每层独立耗尽整份预算。
- 负载超过处理能力时，按任务语义利用平台已有并发限制、背压或有界排队，避免重试和积压放大故障；队列需要容量/保留期限与失败去向，不能无限接收后假称完成。恢复流量逐步放开并观察下游，不能一次重放全部积压；不为简单同步任务强行引入队列。
- 对可重试的瞬态错误使用有上限的退避与随机抖动，遵守服务的重试提示；预算耗尽就停止相同尝试并报告证据，不无限循环。
- 参数、版本、凭据或权限错误先定位并纠正原因；条件未变时重复同一请求通常无益。
- 写入或部署请求超时不代表未执行。先查询任务、资源、提交或部署状态，再决定是否重试。
- 工具支持幂等键时，同一逻辑操作重试沿用原键与参数；新操作使用新键。平台不支持时先比对已有资源和目标状态，不声称仅凭客户端记录能保证只执行一次。
- 平台提供异步任务时保存真实 task/job/deployment ID，通过状态接口恢复；不要反复提交来代替查询。
- 在已有任务记录或合适的持久载体保存简短检查点：目标、当前阶段、已验证结果、待办、请求/提交/部署 ID、证据位置、下一步。恢复时先核对外部状态，不从头重做。
- 没有持久后台执行能力就如实说明；返回任务 ID 不等于任务成功，也不等于关闭聊天后一定继续运行。

## 8. 排障与恢复

生产中断、数据持续受损或影响迅速扩大的紧急任务优先止损恢复：核实目标与影响 → 核对现有恢复记录及适用官方依据 → 执行证据支持的最小恢复 → 验证核心路径与数据状态 → 深入定位根因并补查 4.6 的外部实践。此时不把广泛搜索编程 AI 或替代产品作为恢复前置；但不跳过必要的兼容性检查，也不凭记忆盲目回滚。

普通排障按日志/现状 → 复现或隔离 → 官方资料与已知问题 → 根因 → 最小修复 → 验证进行。已有故障应先减小影响，根因可在恢复后继续调查，不要求查清全部原因才允许恢复。
- 用“假设—证据—判定”组织排查；一次验证一个关键假设，不随机同时修改多个组件，不用临时补丁掩盖错误。
- 先区分代码问题、配置漂移、依赖故障、配额耗尽和部署未生效，再选对应动作。
- 修复没有改善时记录结果，调整假设；没有新证据时停止重复改动，保留可继续排查的信息。
- 若本次发布导致退化，且已有恢复方式适用，在任务范围内执行恢复并重新验证；不要因为回滚命令成功就报告服务已恢复。
- 回退代码前核对数据迁移、资源绑定、外部状态与旧版本兼容性；代码回滚不等于数据库或外部资源回滚。
- 不把“具备排障规则”说成系统已经获得无人值守自愈；后者需要实际后台执行和工具能力。

## 9. 测试、发布与线上验收

- 事先确定与用户目标相符的验收条件和可观察结果；测试要证明请求的改动有效，而非仅证明文件存在或命令能运行。可靠性目标按核心用户路径与实际需要确定，必要时注明统计窗口、成功率、尾部延迟及恢复目标；不照搬 100% 或任意高指标，不用平均值掩盖关键用户失败，优先复用已有观测。
- 上线前：相关模块/静态检查 → 接口契约 → 集成与核心路径 → 回归及适用故障/恢复测试 → 发布条件。上线后：实际版本与配置 → 健康检查 → 核心业务及依赖认证 → 相关指标与状态对账。两阶段各按影响范围执行，不混用。
- 涉及生产行为、架构、接口或持久状态的变更，按 9.1 覆盖相关风险；纯文档与只读任务不触发生产演练。紧急恢复采用第 8 节的最小必要检查，恢复后补足相关回归。
- 简单文档或低影响配置变更只做相关验证；不机械地对每次改动全系统压测。不适用项标记原因，不冒充测试通过。
- 生产发布按现有平台能力和变更影响选择适当方式。有必要且平台支持时使用渐进发布，依据核心功能、错误率、延迟或任务完成情况判断；不强制新增发布平台。
- 记录 commit/version/deployment ID、目标环境和入口；确认生产实际运行的是目标版本。
- 部署后验证真实业务路径和适用的依赖认证/资源访问；仅有 HTTP 200、构建成功或发布成功回执，不足以证明全部功能正常。
- 使用已有日志、指标或追踪定位异常，关注用户可感知结果。一次测试通过不能保证长期零故障。
- 完成后停止无关优化和重复测试；只有实际剩余问题或明确验收要求才扩大验证范围。

### 9.1 上线前复杂场景验证

按本次变更的实际依赖与风险建立简短测试矩阵，记录“场景、初始状态/输入、预期不变量、实际结果、证据、未覆盖项”；同一测试可覆盖多个风险，已有且仍适用的结果可复用。

| 场景类别 | 按适用性验证的行为 |
| --- | --- |
| 功能与契约 | 正常/空值/边界/非法输入，必填与可选字段、错误语义，旧调用方与新实现兼容，核心用户路径真实可用 |
| 并发与重放 | 同一操作重复提交、并发更新、消息重复或乱序；无非预期重复副作用、状态覆盖或数据丢失 |
| 依赖与网络 | 慢响应、断连、限流、上游错误、无效或过期凭据；期限和重试有界，慢依赖不耗尽共享资源并拖垮无关模块 |
| 中断与恢复 | 写入已发生但响应丢失、任务中途终止、重启续办、部分完成；依据真实状态恢复而非盲目重做，最终结果可对账 |
| 容量与持续运行 | 可信峰值、资源/配额边界、积压及恢复；观察尾部延迟、内存/连接增长和下游压力，持续时间按实际风险选择 |
| 升级与回退 | 新旧版本并存、配置继承、数据迁移与回退；无关数据、凭据、绑定保留，恢复路径实际可行 |

- **以整体稳定性验收组合场景**：上线前沿受影响的完整业务链路验证各模块、依赖与共享资源协同，不能用各模块单独通过代替系统通过。根据实际风险选择复杂组合，如“峰值并发 + 下游慢响应/限流”“写入完成但响应丢失 + 重试”“依赖中断 + 任务续办”“新旧版本并存 + 积压恢复”，检查故障传播、资源争用与恢复后的持续运行；不机械穷举所有排列。
- **每项先定义通过条件**：依据实际需求明确端到端成功率、尾部延迟、资源/积压上限、数据一致性及恢复时间等适用标准，覆盖正常、受扰动和恢复后三阶段。验证无非预期重复写入或数据丢失、重试不放大故障、局部失败不拖垮无关核心路径；观察窗口应足以暴露本次相关的泄漏、积压和性能退化，并记录实际负载、时长和环境差异。关键整体稳定性条件未验证或不达标时不发布；执行既定紧急恢复分支时按第 8 节处理，不将其作为普通上线免测理由。不能以短时通过宣称覆盖所有情况或保证长期零故障。
- **优先可控且可重复的验证**：故障注入、压力和破坏性恢复演练使用隔离测试环境或平台提供的测试能力，避免影响真实业务与数据；记录版本、配置差异、随机种子（适用时）和停止条件。无法复现生产特性时注明差异与残余风险，不能把模拟成功当作线上成功。
- **复用成熟工具而非强制安装**：已有测试框架能验证接口就直接使用；多调用方的契约协调确有需要时评估 Pact；测试运行环境允许 TCP 代理且需网络故障注入时评估 Toxiproxy。HTTP 业务错误、身份认证或平台特有行为另用适用的测试能力验证，工具不能替代全部场景。
- **结果决定是否具备发布条件**：相关关键测试失败或必须的正确性/恢复条件未验证时，先修复或完成验证，不能宣称已具备上线条件；不适用项说明理由，未执行项不能标为通过。满足本次发布条件后按原有直接执行规则部署，不增加人工审批；上线后继续核实实际版本和核心业务结果。

## 10. 结果交付与持续改进

简洁报告：实际完成项、变更原因、最终运行状态、关键验证结果、未完成/未验证项和必要证据链接。
- 清楚区分已修改、已提交、已上传版本、已部署、已验证；不要用“完成”掩盖中间状态。
- 关键配置报告已配置/沿用/缺失/未验证，不输出 Secret 值。
- 按任务类型验收：只读检查交付范围、证据、发现与未知项；方案交付候选、取舍、风险和验证计划；实施交付目标差异、相关测试及未部署状态（适用时）；发布交付实际环境/版本和线上结果；紧急恢复交付影响是否停止、核心路径是否恢复与剩余排障事项。不适用的测试、变更记录或上线步骤无需执行，不能将“检查完成”写成“系统已修复”。
- 工具或权限阻塞时说明失败动作和实际原因，继续完成不依赖该阻塞的已授权工作。
- 用真实失败和用户反馈改善工作方法；记录根因、最小修复和验证证据，不为假想问题无限追加条款。
- 需要验证 Skill 决策质量时，优先用已有执行环境和少量真实任务/失败案例比较修改前后版本；预先定义可观察的通过条件，同时覆盖应该改动与应该保持现状、适用原生能力与原生不适用、证据充分与关键证据缺失。补充局部省钱却提高全链路成本、冗余共享故障源、降级保护核心路径、负载变化导致方案排名改变等适用案例。允许多种满足约束的正确方案，不只匹配预设技术名称。
- 比较时保持模型、工具、起始状态与任务条件可比，记录实际结果、无关改动、失败原因和必要成本；重复运行仅用于确认关键行为的一致性，不挑最好的一次冒充可靠性。优先复用现有测试和记录，不为评估新增复杂平台。
- 格式检查和静态情景审查不等于真实 Agent 或生产测试。只有实际执行后才能声称行为验证通过；没有可比实测时，不声称决策准确率已提高或保证零错误。
